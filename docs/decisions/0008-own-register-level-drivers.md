# ADR-0008: Write the drivers at register level instead of using a vendor library

**Status:** Accepted
**Date:** 2026-10-08 (decided on 2026-10-02, when the course drivers were moved to
`reference/`; recorded here once the drivers were working)
**Phase:** 1

## Context

The firmware needs drivers for the clock tree (HSI to PLL), USART2 (TX), I2C1 (master)
and, in Phase 2, SPI1 with DMA. The naive route on an STM32 is ST's HAL, generated by
CubeMX. Material was also at hand from the course: ARM University Program code, ST's
Standard Peripheral Library and a teacher-written I2C driver (kept locally in
`firmware/**/reference/`, git-ignored, outside the Keil project).

The forces:
- the purpose of the project (`CLAUDE.md`): to understand every design decision well
  enough to defend it in an interview, and to produce a repository that shows
  industry-level practice;
- the hard constraints: no dynamic allocation, every blocking loop bounded and flagged,
  and FreeRTOS owns SysTick and the interrupt priority scheme (ADR-0003, ADR-0004);
- what the drivers have to do in an RTOS: timeouts measured in real time, distinct error
  codes, short critical sections around the few operations with deadlines, recovery from
  a stuck bus.

Doing nothing special would mean generating HAL code and calling it.

## Options considered

### Option A: ST HAL (CubeMX)
- How it works: generated initialisation code and `HAL_xxx` calls (`HAL_I2C_Mem_Read`,
  `HAL_UART_Transmit_IT`, `HAL_RCC_ClockConfig`).
- Pros: the fastest way to a working system; tested by ST; covers every peripheral.
- Cons: it hides exactly what an interviewer asks about (the flag sequences, the ACK/STOP
  deadline, the clock order). Its timeouts and `HAL_Delay` rely on a millisecond counter
  incremented by SysTick, which here belongs to FreeRTOS, so the HAL would need a
  different time base. Its internal state and locking model is not ours.

### Option B: ST LL (low-layer) or the Standard Peripheral Library
- How it works: thin functions over the registers (`LL_I2C_GenerateStartCondition`, and
  so on), with no hidden state.
- Pros: close to the hardware, small, no hidden time base.
- Cons: the interesting part is still not written by us: the order of the operations and
  the reaction to each flag. The Standard Peripheral Library is also legacy.

### Option C: the course drivers as they are
- Cons: the teacher's I2C returns nothing on failure, takes the address already shifted,
  has no bounded waits, and its last-byte handling in a multi-byte read depends on timing
  it does not protect (see ADR-0007). They were written for bare metal, not for a task
  that can be preempted.

### Option D: own drivers at register level, from the reference manual
- How it works: each driver is written against RM0383 with the CMSIS device header for
  register and bit names; one step at a time, each step checked on the board.
- Pros: every line can be explained; the API, the error codes, the timeouts and the
  recovery are ours and fit the RTOS; nothing hidden uses SysTick, a heap or a lock.
- Cons: much more work; subtle bugs a vendor library has already fixed are ours to find;
  no vendor testing behind it; only the features implemented exist.

## Decision

Option D. What swung it is the purpose of the project: writing the drivers is the
learning, and being able to say why each register write is where it is. A second,
practical reason came out of the work itself: the behaviour the system needs (bounded
waits in RTOS ticks, a critical section around the receive deadline, self-recovery, one
error code per cause) is not what Options A and C provide.

From the vendor we still use: the CMSIS device header (`stm32f4xx.h`: register and bit
definitions), `core_cm4.h` (the NVIC functions), the Keil device pack's start-up file and
`system_stm32f4xx.c`, and the unmodified FreeRTOS kernel. We do not use HAL, LL or the
Standard Peripheral Library.

## Consequences

- Easier: every register access has a written reason in the code; the drivers fit the
  RTOS rules of the project (static allocation, bounded waits, flagged blocking); the
  whole firmware including the kernel is small (about 18.5 KB of flash and 4.0 KB of
  RAM in the last map, 2026-10-17).
- Harder: each driver carries the risk of mistakes a library would have fixed, and the
  chip's quirks have to be found by us (for example, how the I2C peripheral behaves
  after a reset in the middle of a transfer). Only what is needed exists: USART2 TX at
  115200 (no receive), I2C master at 100 kHz with 7-bit addresses, and SPI1 as a slave
  with DMA (ADR-0010).
- What has not been verified is listed per driver, honestly: the error paths of the clock
  module (ADR-0006), the I2C error paths other than the ones provoked on the board
  (ADR-0007), and the UART bit time on the wire (see `architecture.md`, known gaps). The
  clock frequency and the I2C receive sequence were measured on the wire with a logic
  analyzer (ADR-0006, ADR-0007).
- Rules this created for the SPI driver (Phase 2), which follows them: the same style,
  written and checked one step at a time, with the reasoning in the comments, expected
  register values for the debugger, bounded waits, a status code for every failure, and
  the unverified items written down.
- Revisit if a peripheral is too big for the benefit of writing it (a USB stack, Ethernet,
  cryptography): use the vendor or a middleware then, and record that choice in its own
  ADR.
- The course material stays local-only in `reference/`.

## Interview angle

"I wrote the drivers at register level on purpose: it is a learning project, and I wanted
to be able to explain every flag and every ordering. It also gave me what an RTOS system
needs and the HAL does not give me for free: waits bounded in ticks, one error code per
cause, a critical section only around the few operations with a deadline, and recovery
from a bus error. I know the cost: no vendor testing, so I wrote down what I have verified
on the board and what I have not."
